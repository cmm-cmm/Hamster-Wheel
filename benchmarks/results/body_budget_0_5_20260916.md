# Aggregate body-memory budget — 2026-09-16

Windows release-build measurements of the working-tree `server.max_body_memory`
budget. Nothing here is committed and nothing here is a release claim.

Machine: Windows 11 Pro build 26200, Core i5-12400, 32 GiB, MSVC release build
(`x86_64-pc-windows-msvc`). Both arms are the same binary; `max_body_memory = 0`
disables the budget and restores the previous code path, which is what makes
this an A/B rather than a before/after of two builds.

Sources: [`benchmarks/body_memory_probe.ps1`](../body_memory_probe.ps1) with
`-MaxBodyMemory`, and [`benchmarks/php_worker.ps1`](../php_worker.ps1) with
`-MaxBodyMemory` and `-EchoBodyBytes`.

## What the ceiling is measured against

The probe opens N connections, declares a 1 MiB body on each, sends half of it
and stops, holding the request behind `/delay?ms=10000`. After one second it
samples the Hamster process. This is the workload the earlier investigation
showed was unbounded by `queue_capacity`: bodies still being reconstructed by
the HTTP consumer.

`Refused` counts connections answered `503`. Deltas are from the ready-but-idle
process and include allocator and Hyper connection overhead.

## The ceiling stops tracking connection count

`queue_capacity=128`, one PHP worker, `max_connections` equal to the connection
count in each row.

| accepted connections | budget off | budget 16 MiB | refused at 16 MiB |
|---:|---:|---:|---:|
| 32 | 36.52 MiB | 18.23 MiB | 4 |
| 64 | 72.41 MiB | 18.93 MiB | 13 |
| 128 | 140.59 MiB | 18.87 MiB | 34 |
| 256 | 278.50 MiB | 18.79 MiB | 109 |

FACT: with the budget off the private-memory delta is linear in accepted
connections, 1.09 MiB per connection over this range. With a 16 MiB budget it
is flat at 18.2-18.9 MiB across an eightfold change in connection count.

FACT: at 256 connections the budget reduced the delta by 14.8x.

INFERENCE: extrapolating the off-curve to the shipped `max_connections = 1024`
gives roughly 1.1 GiB, which agrees with the earlier investigation's inference
and is the risk this budget exists to bound.

## The ceiling tracks the configured budget

128 connections, same workload.

| `max_body_memory` | private delta | working-set delta | delta / budget |
|---:|---:|---:|---:|
| 4 MiB | 4.48 MiB | 3.10 MiB | 1.12 |
| 16 MiB | 18.36 MiB | 12.34 MiB | 1.15 |
| 64 MiB | 70.07 MiB | 44.68 MiB | 1.09 |
| disabled | 140.59 MiB | 91.04 MiB | n/a |

FACT: the observed private-memory delta is 1.09-1.15 times the configured
budget. The overhead above 1.0 is Hyper's per-connection parser and write
buffers, which the budget deliberately does not cover, plus the worker's
protocol frame for whichever requests are executing.

INFERENCE: an operator sizing this setting should budget roughly 1.2x
`max_body_memory` for the request-body component of RSS, and size Hyper's
connection component separately through `max_connections` and
`http1_max_buffer_size`.

## Completed bodies waiting in the queue are covered too

128 connections, each sending its whole 1 MiB body, `queue_capacity=128`.

| arm | private delta | working-set delta |
|---|---:|---:|
| 16 MiB budget | 20.06 MiB | 19.46 MiB |
| disabled | 143.93 MiB | 138.19 MiB |

FACT: the reservation travels with the job into the bounded queue, so a body
that has finished reconstructing and is waiting for a worker is still charged.

## Hot-path cost

`benchmarks/php_worker.ps1`, one worker, concurrency 1, 20000 measured requests
per run after 1000 warm-up requests. Medians of the runs in each cell.

### No request body (GET `/hello`), 5 runs

| arm | rps | p50 ms | p99 ms | server CPU us/req |
|---|---:|---:|---:|---:|
| budget 64 MiB | 7086 | 0.137 | 0.246 | 149.219 |
| budget off | 7097 | 0.138 | 0.239 | 151.562 |

FACT: no measurable difference. A request with no body returns before the
budget is consulted, so this is the expected result rather than a lucky one.

### 12-byte POST body (`/echo`), 5 runs then two interleaved 3-run passes

| pass | budget 64 MiB | budget off |
|---|---:|---:|
| 5-run medians | 6728 rps | 6514 rps |
| interleaved pass 1 | 6524 rps | 6803 rps |
| interleaved pass 2 | 6694 rps | 6745 rps |

Server CPU per request, same order: 170.312 / 171.094, 173.438 / 172.656,
164.062 / 178.906 microseconds.

FACT: the sign of the difference flips between passes. Within-arm run-to-run
spread over the 5-run pass was 5903-6859 rps (16%), far larger than the 2-4%
between medians.

### 64 KiB POST body (`/echo`), two interleaved 3-run passes

| pass | budget 64 MiB | budget off |
|---|---:|---:|
| 1 | 3703 rps, 273.438 us | 3733 rps, 275.000 us |
| 2 | 3722 rps, 268.750 us | 3686 rps, 271.875 us |

FACT: medians 3712 versus 3710 rps. No measurable difference.

INFERENCE: the added work per body-bearing request is one `Arc` clone, one
compare-exchange on admission, O(log n) more while an undeclared body grows, and
one fetched subtraction on release. The same change removed a full `Vec` copy of
every reconstructed body, which previously happened in `build_worker_request`.
These are plausibly of similar magnitude, and this harness cannot separate
either from its own noise.

HONEST LIMIT: this measurement can fail to detect a regression below roughly 5%
on these workloads. It does not prove the cost is zero. It does show the cost is
not visible at the HTTP ceiling on a path that is dominated by IPC and PHP.

## Failure behavior

FACT: an over-budget request receives `503` immediately. It is never queued
behind another request and never waits for a release.

FACT: an ignored PHP integration test drives a real worker with the budget set
to exactly one maximum body, saturates it with an in-flight 1 MiB POST, and
asserts that the worker's own executed-request counter does not include the
refused request. The refusal happens on the admission side of the worker
transaction.

FACT: checked-in real-TCP tests assert that the reservation returns to zero
after a served body, a timed-out body, a client that disconnects mid-body, a
refused declared body and a chunked body that outgrows the budget, and that the
server serves normally afterwards in each case.

## What is still outside the counter

Response bodies, the protocol frame a worker builds for an in-flight job, Hyper
per-connection buffers, and allocator fragmentation. The measured 1.09-1.15x
factor above is where they show up.

## Re-measured after the observability addition

The budget was given a startup line, a rate-limited refusal notice on standard
error, and a documented 503 reason body. None of it is on the served path: the
success paths of `acquire`, `grow_to` and `release` are unchanged, the no-body
fast path is unchanged, and the clock read and window compare-exchange run only
when a request is actually being refused.

Interleaved A/B re-run, 12-byte POST `/echo`, 3 runs x 20,000 requests per cell:

| pass | budget 64 MiB | budget off |
|---|---:|---:|
| 1 | 6,045 rps | 6,461 rps |
| 2 | 6,423 rps | 6,369 rps |

Server CPU per request, same order: 178.125 / 175.781 and 181.250 / 183.594
microseconds.

FACT: medians 6,234 versus 6,415 rps, with 6% spread between the two passes of
the same arm. The sign of the difference flips as before. No effect outside
noise.

FACT: the whole re-run sits below the earlier session's 6,524-6,803 rps on the
same scenario. That is machine drift between sessions, and it is why only the
interleaved comparison is quoted.

The no-body A/B was not re-run. `BodyReservation` did not change; only
`BodyBudget`'s own fields did, and a request with no body never reaches them.

FACT: the refusal notice was verified end to end through the real PHP worker
path. With `max_body_memory` set to exactly one maximum body, a saturating
in-flight 1 MiB POST caused a concurrent small POST to be refused and the server
wrote:

```text
body memory budget exhausted: 1 request(s) refused with 503 since start
(server.max_body_memory = 1048576 bytes); reported at most once per 60 s
```
