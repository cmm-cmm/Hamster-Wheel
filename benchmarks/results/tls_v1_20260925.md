# TLS v1 measurements — 2026-09-25

Windows 11 Pro 10.0.26200, 12th Gen Intel Core i5-12400, 31.8 GiB RAM,
Balanced power plan, loopback only. Release `x86_64-pc-windows-msvc` build of
the working tree (rustls 0.23.45, tokio-rustls 0.26.5, aws-lc-rs 1.18.1).
Harness: `benches/tls.rs` (`cargo bench --target x86_64-pc-windows-msvc
--bench tls --features profiling -- <suite>`); Hamster runs as the release
binary in its own process serving static files from a temporary root, both
listeners on one process, the self-signed `localhost` certificate trusted by
the rustls client in the bench process. Three runs per cell, medians, all
three runs shown. The load generator (6 Tokio threads) shares the machine and
also does the client-side TLS work, so TLS rows include client crypto
competing for the same cores. Native Linux: NOT VERIFIED.

Run-to-run noise on this machine is large: the same cleartext cell moved by
up to 20% between sessions (compare the two keep-alive tables). Compare TLS
with cleartext inside one table, not across tables.

## New connection per request, final binary

Every request opens a connection, sends `GET /tiny.txt` reads the response and then resets the connection (zero linger), so neither side accumulates TIME_WAIT across tens of thousands of connections. `https` performs a full handshake each time (client resumption disabled); `https resumed` lets the client resume a TLS 1.3 session. Latency includes TCP connect and the handshake, not the close. Window 3 s.

| Mode | Scheme | C | connections/s median (runs) | MiB/s | p50 ms | p99 ms | Hamster CPU us/conn | connections |
|---|---|---:|---:|---:|---:|---:|---:|---:|

| new full | https | 1 | 651 (651 / 642 / 656) | 0.0 | 1.331 | 2.547 | 785.7 | 5851 |

TLS 1.3 resumption barely changes the rate: resumption skips certificate
signing and verification, but both sides still perform the ECDHE key
exchange, TCP connect and teardown.

`old`; the other rounds agree within a few percent. No throughput, latency or
CPU regression is detected at about 10% resolution. New connections at C8 were
0-5% lower for `new` in all four rounds: inside the noise, but on the same side
each time, so a small accept-path cost is not excluded.

Idle memory per cleartext connection, same A/B setup, 256 and 1,024 idle
keep-alive connections:

| Binary | KiB per idle cleartext connection (N=256 / N=1024) |
|---|---|
| pre-TLS | 26.0 / 25.3 (first session), 26.2 / 25.3 (second) |
| TLS build, TLS branch inline | 31.0 / 29.5, 30.6 / 29.4 |
| TLS build, TLS branch boxed (final) | 26.9 / 25.5 |

The inline TLS branch sized every connection task, cleartext included, for
the rustls handshake and stream state. Boxing it restored the cleartext cost.
