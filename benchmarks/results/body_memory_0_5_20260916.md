# Aggregate PHP body-memory investigation — 2026-09-16

This is a Windows release-build probe of the current 0.5.x body path. It does
not change production behavior and does not claim a release benchmark. The
probe starts one Hamster process with the fixture PHP worker, opens the selected
number of TCP connections, sends a declared 1 MiB POST body, and keeps the
request alive behind `/delay?ms=10000`. After one second it samples
`PrivateMemorySize64` and `WorkingSet64` for the Hamster process and its PHP
children. The process is then terminated so queued requests do not have to
complete serially.

Machine: Windows 11 Pro build 26200, Core i5-12400, 32 GiB, MSVC release build.
The server body deadline was 30 seconds. Measurements are deltas from the
ready-but-idle process; allocator and Hyper connection overhead are included.

Probe source: [`benchmarks/body_memory_probe.ps1`](../../benchmarks/body_memory_probe.ps1).

## Completed bodies, one PHP worker

`queue_capacity=128`, `body=1 MiB`, all connections send their complete body.

| accepted connections | Hamster private delta | Hamster working-set delta | PHP private delta | PHP working-set delta |
|---:|---:|---:|---:|---:|
| 4 | 6.52 MiB | 6.38 MiB | 2.00 MiB | 2.36 MiB |
| 8 | 10.93 MiB | 10.57 MiB | 2.00 MiB | 2.36 MiB |
| 16 | 21.32 MiB | 20.54 MiB | 2.00 MiB | 2.36 MiB |
| 32 | 37.52 MiB | 36.50 MiB | 2.00 MiB | 2.36 MiB |
| 64 | 73.71 MiB | 71.96 MiB | 2.00 MiB | 2.36 MiB |

FACT: the Hamster delta is approximately linear in accepted connections, close
to one body-sized allocation per retained request plus connection/protocol
overhead. The PHP process does not retain the request bodies in this fixture.
The one-second sample is a steady retained-memory observation, not a peak
allocator trace: `BytesMut` is copied into the `WorkerRequest` and an active
worker temporarily builds a protocol frame, so instantaneous transition peaks
can be higher than the sampled delta.

## Queue pressure, 32 connections

`body=1 MiB`, one PHP worker, all bodies complete before sampling.

| queue capacity | Hamster private delta | Hamster working-set delta |
|---:|---:|---:|
| 1 | 6.17 MiB | 5.88 MiB |
| 8 | 14.78 MiB | 13.14 MiB |
| 128 | 37.62 MiB | 36.27 MiB |

FACT: when the queue is full, requests receive the existing pool-pressure
failure and their `WorkerRequest` body is released. Completed-body retention is
therefore bounded by the requests that can be admitted to workers/queue, but a
large queue increases the retained payload linearly.

With four PHP workers and 32 connections, `queue_capacity=8` measured 22.94 MiB
Hamster private delta and `queue_capacity=128` measured 44.15 MiB. The PHP
private delta was 8.02 MiB in both cases, consistent with four worker processes
and their fixture baseline rather than body retention.

## Incomplete bodies bypass queue pressure

With 32 connections, one worker, `queue_capacity=1`, each client sent only 0.5
MiB of a declared 1 MiB body and then paused. The Hamster private delta was
37.58 MiB and working-set delta 26.34 MiB; PHP memory was unchanged.

FACT: queue capacity does not bound bodies still being reconstructed by the HTTP
handlers. The current independent bound is `max_connections` times the body
limit, with allocator/parser overhead; queue capacity only bounds bodies after
they reach PHP pool admission.

## Technical interpretation

INFERENCE: the source ownership model is:

```text
accepted connection
  -> Hyper Incoming / BytesMut while body is incomplete
  -> WorkerRequest Vec after body reconstruction
  -> PhpJob in bounded queue or one worker transaction
  -> dropped after response/error
```

One HTTP/1 connection processes one service future at a time in this path, so
`max_connections` is the useful upper bound on simultaneously owned request
bodies. The queue does not add an independent population on top of those
connections; jobs came from the same accepted connections. Encoding a request
for a worker creates short-lived additional frame storage, explaining why the
measured slope is above exactly 1 MiB/request.

INFERENCE: the practical aggregate bound is predictable but can be large. With
the default `max_connections=1024` and a 1 MiB body limit, a coordinated set of
slow clients can approach roughly 1 GiB of body/parser memory before the 30-second
deadline, regardless of `queue_capacity`. The 1024 figure is a configuration
bound, not a claim that ordinary traffic reaches it.

HYPOTHESIS: a global byte budget would reduce worst-case memory but would need a
reservation/release policy around partial reads, queue admission and timeout
cleanup. It could add atomics/contended coordination to every body frame and
would have to choose between backpressure, 413, and 503 semantics. These
measurements establish the risk; they do not yet establish that a particular
budget mechanism is worth that complexity.

No production aggregate budget was added in this pass. The next decision should
compare an operationally lower `max_connections`/body limit against a measured
byte-budget prototype under the same incomplete-body workload. No protocol or
worker architecture change is required to make that decision.
