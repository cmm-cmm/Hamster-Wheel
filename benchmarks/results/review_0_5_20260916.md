# HTTP/Transport 0.5 milestone review — 2026-09-16

Measurements taken while reviewing the four 0.5 slices as a milestone candidate.
They are resource-bound observations, not throughput benchmarks, and nothing
here is a release claim.

Machine: Windows 11 Pro build 26200, Core i5-12400, 32 GiB, MSVC release build
(`x86_64-pc-windows-msvc`), the same binary the body-budget results used.

The probes were throwaway scripts and are not checked in, so each procedure is
written out below in enough detail to repeat by hand. No production code was
changed to take these.

## Response-body memory is unbounded

Procedure: serve a directory containing a 256 MiB file through a `static`
location with `max_connections = 64` and `header_read_timeout = 30`. Open four
TCP clients, each with `ReceiveBufferSize` set to 512 bytes before connecting, so
the kernel cannot drain the response on the application's behalf. Each sends
`GET /huge.bin HTTP/1.1` with a `Host` header and then reads nothing. Sample the
server's `PrivateMemorySize64` every 20 ms for four seconds and keep the peak.

| | |
|---|---:|
| idle private memory | 1.47 MiB |
| peak private delta, 4 stalled clients | 1026.4 MiB |
| per in-flight request | 256.6 MiB |

FACT: the delta is one complete copy of the file per in-flight request, which is
what `static_files::serve` does — it calls `tokio::fs::read` and hands the whole
body to `Full::new`.

FACT: this is sixteen times the entire default `max_body_memory`, reached with
four ordinary requests.

An earlier attempt with eight clients and a 64 MiB file measured only 0.75 MiB.
That was a sampling failure, not a contrary result: loopback drained 64 MiB
responses faster than a 250 ms sampling interval could see. The 256 MiB file with
20 ms sampling is the run that resolves it, and the source settles the mechanism
independently of either measurement.

## The hold is bounded in time, not in size

Procedure: the same static root with `max_connections = 1`. Client A requests the
256 MiB file with a 512-byte receive buffer and never reads. After two seconds,
client B connects and requests a different file, and the time until B receives
its first response byte is measured.

| `header_read_timeout` | B answered after | B's status |
|---:|---:|---|
| 5 s | 3.1 s | 200 |
| 10 s | 7.0 s | 200 |

FACT: in both runs B was served `header_read_timeout` minus the two-second delay
after A stalled, and the server's private memory returned to 1.6 MiB. A stalled
response write does not hold a connection slot indefinitely.

INFERENCE: Hyper's header deadline covers the response-write phase, which is
more than `doc/HTTP_TRANSPORT_0_5.md` claims for it in the second slice. The
favourable behavior is load bearing and no test pins it.

Two hypotheses raised at the start of the review were refuted by these runs: that
a non-reading client holds a connection slot indefinitely, and that graceful
shutdown hangs on one. A shutdown driven with a non-reading client attached
completed in about one second.

## A stalled declared Content-Length denies other POSTs

Procedure: a PHP worker location with `max_body_memory = 4194304`,
`body_read_timeout = 20`, `max_connections = 64`, two workers. Four clients each
send a complete request head declaring `Content-Length: 1048576`, then send
exactly one body byte and stop. After 800 ms, one ordinary small POST and one
ordinary GET are sent on fresh connections.

```text
small POST -> HTTP/1.1 503 Service Unavailable
GET        -> HTTP/1.1 200 OK
```

The server also wrote, unprompted:

```text
body memory budget exhausted: 1 request(s) refused with 503 since start
(server.max_body_memory = 4194304 bytes); reported at most once per 60 s
```

FACT: four clients holding 4 MiB of declared but unsent body denied POST service
to every other client, while GET traffic was unaffected. The hold lasts until
`body_read_timeout` expires.

INFERENCE: at the 64 MiB default the same denial costs an attacker 64
connections. The budget traded a memory-exhaustion risk for a POST-availability
risk. The trade is still favourable — the process survives, GET and static keep
serving, the hold is time bounded, and the condition names itself — but it is a
property 0.5 introduced.

FACT: the condition was diagnosable without instrumenting anything, which is what
the observability requirement was for.
